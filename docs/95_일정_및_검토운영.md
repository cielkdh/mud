# 95. 일정·작업·리뷰 운영계획

## 1. 일정의 가정과 한계
착수일/실투입인원/숙련도/기존 코드/실물 자산완성도는미제공이다. 따라서임의날짜를확정하지않고 D0 부터의**선행제약최단경로**와총공수를제시한다.1 인일은6 집중시간,작업일달력은주5 일을설정가능한기본값으로둔다. 이문서의공수는프로젝트개발용계획값이며문서생성소요시간안내가아니다.

Task별 O/M/P 가중치의 기계 계산은 **약 950 인일**, 초기 계획 범위는 **750~1,200 인일**이다. DAG 선행경로 계산값은 **약 141 작업일**이지만 무제한 인력·대기 0 가정이므로 일정 하한이나 약속이 아니다. 아래 소수점은 계산 재현용이며 추정 정밀도를 뜻하지 않는다. 한 사람이면 컨텍스트 전환/검토 대기, 여러 사람이면 역할별 용량/schema 경합/QA 병목을 다시 산정한다.

현재 활성 범위는 `관리데이터/phases.json` 각 Phase의 `active_function_ids`가 유일한 source of truth이며 초기값은 **P0 기준선·빌드 lock 기능만**이다. 672개 Task와 아래 PERT 값은 요구사항 추적·상대 선행관계용 후보치다. 대상 파일, 기존 API/재사용 지점, 담당자·리뷰어, build/test 명령, 증거 경로, 필수 결정이 확인되기 전에는 P1~P25 착수일·납기로 사용하지 않는다. `SchemaBaselineMode`의 실제 Room 증거는 P3에서 확인한다.

역할은 설계 책임 경계를 뜻하며 실제 사람을 임의 지정하지 않는다. Task는 해당 역할의 **실명 담당자 1명과 독립 리뷰어 1명**이 등록되기 전 `IN_PROGRESS`로 바꿀 수 없다. 아래 Phase 표의 `미지정`은 실명 staffing 상태이며 이 규칙에 따라 차단으로 취급한다.

활성 기능의 계약·fixture Task는 원자 Assertion을 검토하기 위해 먼저 착수할 수 있다. 그 밖의 구현 Task는 해당 기능의 `REQUIRED`/`DATA`가 모두 `APPROVED_REQUIREMENT`이 된 뒤에만 `IN_PROGRESS`로 바꾼다. 요구가 아닌 자동 후보는 결정 ID를 남기고 강도를 재분류하며, 유예할 기능은 `active_function_ids`에서 제외해 구현 자체를 열지 않는다. authoritative save 필드는 불명확한 필드 단위 유예를 허용하지 않으며, Phase Gate는 채택 Assertion의 `IMPLEMENTED`와 `DIRECT_TEST` 또는 `APPROVED_MANUAL_REVIEW` 증거를 요구한다.

`관리데이터/tasks.json`, `tests.json`, `decisions.json`을진행원본으로사용한다.마스터/90/91 은작성일기준설계 snapshot 이고변경된진척은`98_진행현황_대시보드.md`에재생성한다. `검증도구/rebuild_status.py`를실행하면최신집계를만든다.검증되지않은상태를 PASS/DONE 으로자동승격하지않는다.
