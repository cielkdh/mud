## 독립 문서의 구성

각 Phase는 개요와 목표, 선행 조건, 기능 범위, 입력/반환/메소드, 처리 흐름, 상태, 객체 책임, DB/SQL, Transaction/동시성/Thread, 예외 처리, Task, 의존관계, Test, Regression, DoD, 리스크, 이전·다음 Phase 인계를 포함한다. 담당 원문의 수치·카탈로그·화면 규칙은 해당 문서의 부록에서 직접 확인할 수 있다.

## 기준선과 검토 상태

원문은 요구 근거이며 Phase 문서는 구현 제안이다. 관리 JSON은 계획·상태 데이터, 검증 스크립트는 문서 및 제안 SQL 검사 도구다. 게임 코드나 Android 실행 결과를 작성한 것은 아니다.

실제 저장소·자산·기기 검증 자료가 제공되지 않았으므로 초기 관리 기준선은 모든 Task가 `NOT_STARTED`, 모든 게임 Test가 `NOT_RUN`이다. 기존 프로젝트의 실제 진척을 조사해서 확정한 값이 아니다. 설계 보완안은 프로젝트 리뷰 및 승인이 필요하다.

요구사항 3,135개는 **최상위 절 단위 묶음**이다. 각 절 내부의 모든 하위 조건을 원자적인 Test assertion으로 검수한 결과와 혼동하지 않는다. 해당 세부 수용성 검토를 기능별 계약·검증 Task 및 Full 콘텐츠 감사에 명시했다.

## 파일 사용과 변경 관리

원문 부록은 `details`로 접혀 있다. 이를 지원하지 않는 Markdown 렌더러에서도 텍스트 편집기로 전체 내용을 읽을 수 있다. source/Task/Test에 명시적 anchor를 사용하며 모든 파일은 UTF-8이다.

`관리데이터/tasks.json`의 담당자·상태·선택적 Phase/중간 revision 참조·실측 공수, `tests.json`의 상태·결과·증거를 갱신한다. commit·PR·revision 참조만으로 PASS·`DONE`·승인을 판정하지 않는다. `decisions.json`의 결정 승인과 관련 Task의 `blocked_by`는 함께 검토한다. 마스터와 90~96번 문서는 최초 설계 기준선이며, 변경 시 같은 revision으로 갱신한다. 실제 진행 현황은 아래 도구로 재생성한다.

## 검증/현황 재생성

```text
py -3 검증도구/rebuild_status.py
py -3 검증도구/validate_docs.py
```

Windows Python Launcher(`py`) 기준이며 Python 3.10 이상 설치가 필요하다. 런처만 있고 인터프리터가 없으면 실행되지 않는다. 다른 OS에서는 `python3`로 바꿔 실행한다. 첫 명령은 기록된 진행 상태를 집계하며 `PASS`나 `DONE`을 자동 생성하지 않는다. 두 번째 명령은 원본 해시, ID, 문서 참조, DAG, 전역 계약, 제안 DDL 및 소수의 SQL 제약조건을 검사한다. 실제 게임 테스트를 실행하는 명령이 아니다.
